# Evaluation Criteria

## Criteria and Why Each Matters

| Criterion | Why It Matters |
|---|---|
| **Developer experience** | If the tool is slow, awkward, or interrupts flow, developers will quietly stop using it regardless of its other strengths. This is the criterion that determines whether adoption is real or nominal. |
| **Security** | The tool will touch source code and potentially proprietary or sensitive systems. Weak security here is a risk to the whole organization, not just to the tool's own use case. |
| **Enterprise integration** | A tool that doesn't fit existing IDEs, repositories, and identity/access systems creates friction that undermines both adoption and governance. |
| **Governance** | Enterprise use requires audit trails, usage controls, and a clear story for risk and compliance stakeholders — this isn't optional at scale. |
| **Cost** | Total cost at enterprise scale, not list price per seat — including the cost of poor adoption if the wrong tool is chosen. |
| **Adoption potential** | A separate consideration from developer experience: does this tool fit how teams already work, or does it require workflow changes that create resistance regardless of the tool's quality? |
| **Supportability** | Can the organization actually support this tool operationally — documentation, vendor responsiveness, internal expertise? |
| **Implementation complexity** | How much work is required to deploy, integrate, and maintain this tool, independent of its ongoing cost? |

## Why Define Criteria Before Evaluating Tools

Defining criteria first, before looking at specific tools, prevents the criteria from being reverse-engineered to justify whichever tool is already the informal favorite. It also gives every stakeholder group a chance to see their priority represented in the framework before the scoring starts, which makes the eventual recommendation easier to defend.
